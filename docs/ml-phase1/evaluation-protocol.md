# Real detector evaluation protocol (unexecuted)

The greater-than-95% heavy-burr recall and at-most-100-ms edge inspection latency are **targets**, not measured results. The scenario simulator has no model accuracy. The training template is `software/ml/training/training-config.template.json`; nulls must be resolved using approved data, compute, and component tolerances before any training run. Its class list is deliberately unresolved: the current simulator's `burr` class is not an approved heavy-burr labeling taxonomy, and a trained model must be paired with a new compatible profile version.

1. Freeze a component profile and annotation guide. Obtain a representative, licensed real dataset with clean, minor, heavy, ambiguous, geometry-defect, and lighting/quality cases. Keep part, batch, session, and source IDs. Measure physical tolerances independently of RGB appearance where acceptance claims require them.
2. Detect exact and near duplicates, then partition by physical part (or a documented stronger provenance group). Keep a genuinely held-out test set untouched while selecting architecture, preprocessing, and PASS/FAIL/RECHECK thresholds on training and validation only. Record group counts, class balance, source mix, and any unknown provenance. A split with missing groups is not leakage-free.
3. Report image-level and defect-level heavy-burr recall `TP/(TP+FN)` and precision `TP/(TP+FP)`, including the counting policy for RECHECK. Report false acceptance of actually unacceptable parts, false rejection of acceptable parts, RECHECK rate, confusion matrix, and per-class counts/rates. Report localization criteria (IoU and matching policy) for defect-level metrics. Keep geometry and burr failures separate in analysis while evaluating the final combined decision.
4. Plot reliability/calibration of predicted confidence on validation data; select thresholds before opening held-out test labels. Stratify by lighting, orientation, part batch, camera, blur, glare, and occlusion. Report uncertainty and unsupported cases explicitly. Repeat with new component profiles; do not assume cross-component generalization.
5. Measure inference latency and total trigger-to-output latency separately on target Orange Pi 5 hardware, including preprocessing, decision, I/O, and logging. Report sample count, distribution (median/p95/max), model size, peak memory, software/runtime versions, temperature, and power mode. Desktop replay timing is not hardware evidence.
6. For each performance claim, provide numerator/denominator, confidence interval (for example, Wilson interval for binomial recall), and the sample-size rationale. A point estimate above 95% from a small test set does not establish the target with high confidence. Preserve failed and inconclusive trials. Compare ONNX and RKNN outputs on the same held-out images before deployment.

No model training, export, dataset download, or Orange Pi benchmark is performed in this phase.
